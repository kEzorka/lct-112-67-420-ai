# M6. Адаптация — 28.09.2026

Ветка `ai/m6-adaptation`, узел G. Веха M6 (`docs/ai/agent-prompt.md`, раздел 6.7–6.9):
подсказки и режимы (D-041), сложность (D-043), профиль подготовки и рекомендации
(D-044, D-045, C-07, C-08), аналитика типичных ошибок группы ([ТЗ]). Узел F2 (параллельно,
`ai/src/dds_ai/judging/`, `ai/calibration/`, `docs/ai/calibration-report.md`,
`docs/ai/bench/llm-cpu.md`) не тронут.

## 1. Что сделано

### Подсказки и режимы (6.7, D-041)

- `ai/src/dds_ai/contracts/mode.py` — `TrainingMode` (guided/independent), `AttemptTrack`
  (guided/independent/supported) с `counts_toward_independent_rating`.
- `ai/src/dds_ai/hints/track.py` — `attempt_track()` вычисляет трек из режима и события
  `HelpRequested` (контракт `HintShown`/`HelpRequested` уже существовал в `contracts/events.py`
  с M0 — в этой вехе он впервые используется); `can_show_guided_hint()`; `HintDenied`.
  Самостоятельный режим буквально не показывает подсказку о правильном действии до
  завершения (D-041) — запрос помощи меняет только классификацию попытки (трек `supported`,
  исключение из самостоятельного рейтинга), не открывает содержимое эталона во время самой
  попытки; см. п. 5.
- `ai/src/dds_ai/cycle/session.py::TrainingSession` — новый параметр `mode`; методы
  `show_hint()` (только guided, пишет `HintShown`), `request_help()` (только independent,
  пишет `HelpRequested`), свойство `track`. `Evaluation.track` — трек попытки на момент
  оценки, доступен вызывающему коду для решения о зачёте в самостоятельный рейтинг (сам
  зачёт в рейтинг — вне ИИ-контура, D-047).
- `ai/src/dds_ai/contracts/remarks.py::ErrorExplanation` — цепочка ошибка → доказательство →
  упражнение (Q&A 8, D-045). `ai/src/dds_ai/hints/explain.py::explain_errors()` строит её из
  замечаний-ошибок ученика (`Remark.counts_as_error`, исключает `technical_fault`/
  `source_uncertainty`/`info`), упражнение — по типу замечания из
  `ai/config/exercises.ru.json` (рабочая конвенция команды, не пункт реестра решений).

### Сложность (6.8, D-043)

- `ai/src/dds_ai/contracts/difficulty.py` — `DifficultyFactor` (5 факторов из реестра),
  `DifficultyWeights` (версия + неотрицательные веса всех 5 факторов), `DifficultyVector`
  (0/1/2 по каждому), `DifficultyScore`/`FactorContribution` (сумма = Σ level×weight, видна
  по фактору), `FactorProposal`/`DifficultyProposal` (объяснение по фактору).
- `ai/src/dds_ai/difficulty/compute.py::score()` — детерминированный расчёт; веса ≥ 0
  (проверено валидатором контракта) делают рост уровня фактора структурно
  неубывающим для суммы — не только по тесту.
- `ai/src/dds_ai/difficulty/propose.py::propose_vector()` — **правило, не LLM** (решение
  команды, как `card.address`/`manual.grammar` в M5): каждый фактор считается по наблюдаемым
  свойствам уже опубликованного сценария (неизвестные факты → неоднозначность, число
  существенных фактов → обстоятельства, `RoutingDecision.services` или наличие факта
  `services` → службы, `omissible`-факты → дополнения, `drop_after_turns`/`dial_outcomes`
  собеседника → речевые осложнения); `rationale` — по каждому фактору.
- `ai/src/dds_ai/difficulty/band.py` + `ai/config/difficulty.json` — версия весов (начальные
  равные, `difficulty-w01-draft-1`) и рабочие границы low/medium/high; сложность нигде не
  ссылается на нормативы 30/180 (C-01) — они не затронуты.
- Границы уровней и итоговый вектор **не публикуются** этим узлом — по D-043 их утверждает
  преподаватель; это действие вне ИИ-контура (нет соответствующего UI/бэкенда — B04).

### Профиль подготовки (6.9, D-044, C-07, инвариант 13)

- `ai/src/dds_ai/contracts/profile.py::SkillProfile` — совместимо расширен: `difficulty_band`
  (по умолчанию `"all"`) и `track` (по умолчанию `independent`) — оба с дефолтами, старые
  вызовы (`test_contracts.py`) не сломаны. Профиль — один документ на сегмент
  (dds_profile × сложность × режим), не единая структура с тремя измерениями внутри: так
  «профиль по ДДС, сложности и режиму отдельно» (D-044) реализуется без разрастания схемы.
- `ai/src/dds_ai/profile/build.py::build_profile()` — фильтрует попытки по сегменту **и**
  `ScoreVersion.summary.valid_score` (C-07, инвариант 13); группа рубрики — среднее
  `CriterionResult.value` по проверенным критериям сегмента, `attempts_used` — число разных
  попыток, внёсших значение в группу. Без наблюдений в сегменте — `insufficient_data`, без
  придуманного уровня. Экспертная поправка не требует отдельного кода: вызывающий код просто
  передаёт актуальную версию `ScoreVersion` для попытки (append-only история версий уже
  гарантирует, что это и есть поправка) — `build_profile()` — чистая функция от переданного
  списка `AttemptRecord`, повторный вызов с обновлённым входом и есть пересчёт.

### Рекомендации (6.9, D-045, C-04, C-08)

- `ai/src/dds_ai/contracts/profile.py::PoolTask`/`TaskPool` — опубликованный преподавателем
  пул одного `dds_profile`, с `difficulty_rank` (порядок) и `weak_groups` (какие группы
  рубрики тренирует). `Recommendation` расширен: `source_score_versions` (версии оценок,
  на которых построен профиль), `superseded`/`superseded_reason`, `teacher_action`/
  `teacher_action_by`/`teacher_action_at`, `TeacherAction` — полный набор полей аудита C-08.
- `ai/src/dds_ai/profile/recommend.py::recommend()` — детерминированное правило (основа):
  задание только из `pool.tasks` того же `dds_profile`; при `insufficient_data` или пустом
  пуле — `unavailable` с понятной причиной, без генерации эталона на лету; повышение
  уровня — не больше чем на один сосед (`difficulty_rank` ≤ текущий+1), и только когда у
  профиля достаточно доказательств (`MIN_ATTEMPTS_FOR_LEVEL_UP = 3` — рабочая конвенция
  «первых занятий» из D-045, не пункт реестра); выбор нацелен на самую слабую группу
  (`weak_groups`). Опциональный `Recommender` (порт, `ports.Recommender`) переранжирует
  кандидатов правила через `FaultInjector`; его отказ или выход вне множества кандидатов —
  не тихая подмена, а `unavailable` (если преподаватель не назначил `teacher_sequence`) или
  использование этой последовательности (C-04, «рекомендатель недоступен → последовательность
  преподавателя»).
- `mark_superseded()` — неприменённые рекомендации помечаются устаревшими после пересчёта
  (новый `Recommendation` через `model_validate`, не `model_copy` — так валидатор
  `superseded_reason` реально перепроверяется, не обходится); уже применённые (`applied_ids`)
  остаются историческим фактом без изменений. `apply_teacher_action()` — фиксирует действие
  преподавателя, не создавая нового решения по существу.

### Аналитика типичных ошибок группы (6.9, [ТЗ])

- `ai/src/dds_ai/contracts/analytics.py::ErrorFrequencyBucket`/`GroupErrorReport`.
- `ai/src/dds_ai/analytics/group_errors.py::build_group_error_report()` — частота замечаний
  по типу D-037 × группе рубрики × `dds_profile` × сложности, только по попыткам с
  `valid_score = true`; каждый счётчик раскрывается до `attempt_ids`. Технические сбои
  (`technical_fault_count`) и доля `not_checked` (`not_checked_ratio`) считаются отдельно и
  по всем рассмотренным попыткам (не только валидным) — по выводу калибровки M5 («не проверено»
  18,5% на синтетике, доля должна быть видна явно, не спрятана внутри счётчика ошибок).

### Контракты

`ai/src/dds_ai/contracts/__init__.py::SCHEMA_MODELS` пополнен 9 схемами: `error-explanation`,
`difficulty-vector`, `difficulty-weights`, `difficulty-score`, `difficulty-proposal`,
`task-pool`, `group-error-report` (новые) + перегенерированы `skill-profile` и
`recommendation` (совместимое расширение — старые поля не удалены и не переименованы).
`CONTRACTS_VERSION` не менялся (`0.3.0-draft`) по инструкции узла — версию поднимает
оркестратор при слиянии. `contracts/README.md` — таблица владения дополнена новыми схемами.

## 3. Замеры

Не применимо: веха M6 — детерминированные правила и контракты, без вызова моделей на
реальных весах (опциональный `Recommender` в этом узле проверен только `FakeRecommender`/
инъекцией отказа, ни один реальный адаптер рекомендателя не существует — его нет ни в одном
узле M0–M5). Задержки/пропускная способность аналитики (цель «отчёт ≤30 с», раздел 6.9) не
замерены на объёме, соответствующем пилоту — только структурные unit-тесты на единицы
записей; функция чистая и без I/O, за исключением загрузки конфигурации сложности/упражнений
из JSON при каждом вызове `hints.explain_errors`/`difficulty.score` без явного набора
данных — это не оптимизировано (нет кеша), при большом объёме записей на попытку это не
узкое место (сортировка/группировка O(n log n) от числа замечаний одного отчёта), но
неоптимизированная загрузка JSON на каждый вызов `load_exercises()`/`load_weights()` без
переданного словаря — стоит вынести в разовую загрузку на стороне вызывающего кода
(сервисного слоя), если он появится.

## 4. Что не проверено и почему

- **Публикация вектора сложности и границ уровней преподавателем** (D-043: «преподаватель
  публикует итог», «границы уровней утверждает преподаватель») — в этой вехе нет UI/бэкенда,
  которому это принадлежит (граница 4.2 промпта); `ai/config/difficulty.json` — рабочие
  границы команды, не утверждённые заказчиком/преподавателем.
- **Реальный `Recommender` (ML-модель ранжирования).** Ни в одном узле M0–M6 не выбрана и не
  подключена модель для этой роли (в отличие от `SemanticJudge`, у которой есть
  `LLMSemanticJudge` из M5) — деградация проверена инъекцией отказа
  `FaultInjector.inject(ComponentName.RECOMMENDER, ...)`, не реальным сбоем настоящей модели.
  Соответствует объёму D-045: «детерминированное правило — основа; `Recommender` —
  опционально» — основа реализована и покрыта тестами, опция — только контрактом и путём
  деградации.
- **Хранение профиля/рекомендации и настоящий `ScoreVersion` от бэкенда.** `build_profile`/
  `recommend` — чистые функции от переданных `AttemptRecord`/`SkillProfile`/`TaskPool`;
  откуда вызывающий код берёт актуальную версию `ScoreVersion` (последнюю по попытке) и как
  формируется `TaskPool.pool_snapshot_id` при реальной публикации пула — решает бэкенд (B04),
  здесь не эмулируется.
- **Интеграция подсказок в реальный UI.** `show_hint()`/`request_help()` — методы
  `TrainingSession`, вызывающая сторона (клиент/бэкенд) решает, когда их вызывать; сама
  логика «что показать в подсказке» (текст демонстрации/пошагового действия) — вне ИИ-контура
  в этой вехе, `show_hint(text)` принимает готовый текст, не генерирует его.
- **Производительность аналитики на объёме пилота** («отчёт ≤30 с», 6.9) — не замерено, см. п. 3.
- **Содержимое `ai/config/exercises.ru.json`** — по одному упражнению на тип замечания D-037,
  без учёта конкретного критерия/сложности; это черновик для демонстрации цепочки «ошибка →
  доказательство → упражнение», не методически проверенный набор упражнений.
- **`GroupLevel.attempts_used` при пересечении критериев одной попытки с несколькими
  группами** — засчитывается один раз на группу (правильно), но при очень редких сегментах
  (единичные попытки) уровень группы может быть основан на одном-двух критериях, а не на
  представительной выборке; порог «достаточно данных» для профиля не задан (только для
  рекомендации через `MIN_ATTEMPTS_FOR_LEVEL_UP`) — открытый вопрос ниже.

## 5. Решения, принятые по ходу

- **Помощь в самостоятельном режиме не открывает подсказки во время попытки** — только меняет
  классификацию (`track = supported`). Буквальное прочтение D-041/6.7: «подсказки по
  правильному действию не показываются до завершения» — без исключения для случая после
  запроса помощи. Разбор ошибок после завершения (`explain_errors`) одинаково доступен в
  обоих режимах — это и есть отложенная помощь, а не подсказка во время попытки. Если продукт
  ожидает немедленную подсказку по запросу помощи в самостоятельном режиме — это отдельное
  решение, меняющее поведение, а не расширение текущего контракта; см. вопрос ниже.
  (Черновая версия этой правки содержала `can_show_correct_action_hint(mode, help_requested)`,
  разрешавшую подсказку сразу после запроса помощи в самостоятельном режиме — она удалена как
  противоречащая буквальному тексту решения, а не как ошибка кода.)
- **Профиль — документ на сегмент, не одна структура с тремя измерениями.** `SkillProfile`
  получил `difficulty_band`/`track` с дефолтами вместо вложенной структуры «профиль → сложность
  → режим → группы»: проще контракт и совместимее с уже принятой схемой `GroupLevel`
  (`ai/src/dds_ai/contracts/profile.py`), вызывающий код запрашивает нужный сегмент явно.
- **`difficulty_band` — производный ярлык (`low`/`medium`/`high`), не хранится в `Scenario`.**
  `contracts/scenario.py` (владение узла E, M4b) не тронут: сложность считается по
  сценарию на лету через `propose_vector`/`score`/`band_for`, не требует нового поля контракта
  и не создаёт конфликт редактирования с параллельными узлами.
  Правильность: **не проверено принятой практикой** этого граничит с некоторым риском
  расхождения, если два вызова используют разные версии `ai/config/difficulty.json` для одного
  и того же сегмента — на это указывает `weights_version` в `DifficultyScore`, но сопоставление
  версии с сегментом профиля — на совести вызывающего кода (аудит C-08 хранит
  `selection_rules`/`aggregation_rules`, а не отдельно `weights_version` профиля — versioning
  сложности сейчас не входит в `SkillProfile.aggregation_rules`, только в `difficulty_band`
  как готовый ярлык).
- **`MIN_ATTEMPTS_FOR_LEVEL_UP = 3`** — рабочая конвенция «первых занятий» (D-045 «на первых
  занятиях... одним соседним уровнем», без числа); задокументирована в коде и здесь как
  требующая утверждения, не W-03/W-01 значение.
- **`Recommendation`/`SkillProfile` меняются только совместимо**: новые поля — с дефолтами
  (`difficulty_band="all"`, `track=independent`, `superseded=False`, `teacher_action=None`);
  существующий `test_contracts.py` (узел M0) не менялся и остаётся зелёным без правок.
- **`mark_superseded`/`apply_teacher_action` через `model_validate(model_dump() | update)`,
  не `model_copy(update=...)`** — `model_copy` в pydantic v2 не перепроверяет валидаторы, а у
  `Recommendation` есть кросс-полевые инварианты (`superseded ⇔ superseded_reason`,
  `teacher_action ⇔ teacher_action_by/at`); обход валидации на объекте аудита противоречил бы
  самому смыслу аудита.

## 6. Риски и вопросы к команде

- **Немедленная подсказка по запросу помощи.** Решение п. 5 (помощь не открывает подсказку
  во время попытки, только помечает трек) — буквальное прочтение реестра, но может не
  совпадать с ожиданием продукта («попросил помощь — получил подсказку сейчас же»). Если это
  неверно, нужно явное решение оркестратора/заказчика, меняющее `hints/track.py` и
  `TrainingSession.request_help()`.
- **Согласие семантического оценивателя (M5, 59% против порога 85%)** напрямую влияет на
  объём `valid_score`-попыток, которые вообще смогут построить профиль: `card.circumstances`/
  `manual.additions`/`voice.facts_transferred` часто уходят в `not_checked` → `provisional` →
  не проходят фильтр `build_profile`. На пилоте с реальными учениками профиль по многим
  сегментам может подолгу оставаться `insufficient_data` не потому, что учеников мало, а
  потому что оценка часто предварительная — это системный риск M6, а не дефект самой M6
  (согласуется с вопросом узла F, `docs/ai/progress.md`, волна 3).
- **Порог «достаточно данных» для самого профиля** (не только для повышения сложности
  рекомендации) не задан явно — сейчас профиль показывает `attempts_used` как есть, даже
  если это 1 попытка; решение о минимальном пороге для «показывать уровень в отчёте
  преподавателю» (D-046) — вне объёма этого узла, но становится актуальным при подключении
  отчётности.
- **`weights_version` сложности не входит в `AttemptVersionSnapshot`/аудит профиля явно** —
  `DifficultyScore.weights_version` существует, но ничто не проверяет, что профиль/
  рекомендация одного сегмента построены на одной версии весов сложности при смене
  `ai/config/difficulty.json`; для пилота стоит либо закрепить версию весов в
  `AttemptVersionSnapshot.difficulty_config` (поле уже есть в контракте `scoring.py` с M0,
  сейчас не заполняется ни одним узлом), либо явно решить, что переклассификация сегмента при
  смене версии весов — ожидаемое поведение.
