# M4b. ИИ-оператор 112 и генерация сценариев — 28.09.2026

Ветка `ai/m4b-scenarios`, узел E. Вторая часть вехи M4 (`docs/ai/agent-prompt.md`, раздел 6.5):
генерация входной карточки, черновиков сценариев для преподавателя, структурированного
эталона, жизненный цикл черновика, gate публикации C-03 и синтетический набор сценариев с
матрицей покрытия. Первая часть M4 (база знаний/RAG, NLP) сделана узлом C (M4a, влито) —
этот узел использует её контракты (`contracts/knowledge.py`, `KnowledgeIndex.search()`) как
внешний API, не переделывая их.

## 1. Что сделано

**Контракты** (`ai/src/dds_ai/contracts/`, зарегистрированы в `SCHEMA_MODELS`,
`CONTRACTS_VERSION` не менялся — осталось `0.2.0-draft`):
- `scenario.py` — совместимые дополнения: `ScenarioFact.variant_values` (заранее утверждённые
  автором сценария равнозначные формулировки известного факта) и `ScenarioFact.omissible`
  (факт может быть опущен в сгенерированной карточке); `Scenario.dds_profile` (условный профиль
  ДДС, по умолчанию `"profile-1"` — не ломает уже влитые синтетические сценарии узла A) и
  `Scenario.diagnostic` (диагностический сценарий C-03); `CriterionRubricLink` и
  `ScenarioReference.criteria_links` (привязка эталона к группам рубрики и источникам, 6.5.3);
  новый инвариант — `expected_fields` не может ссылаться на факт, которого нет среди известных
  `published_facts` (защита от рассинхронизации эталона и карточки).
- `scenario_lifecycle.py` (новый файл) — `ScenarioStatus` (draft → validated → approved →
  published → archived), `GenerationInputs`/`GenerationMeta` (основание генерации — версия
  модели/шаблона, использованные фрагменты, версия корпуса, инвариант 6), `ScenarioDraftRecord`
  (черновик/версия сценария с её местом в жизненном цикле, `revises`/`teacher_comment` для
  исправленного черновика).

**Генерация карточки** (`ai/src/dds_ai/scenarios/card_generation.py`):
- `generate_card()` — детерминированная базовая реализация (6.5.5): чистая функция
  `(Scenario, seed) → IncidentCard`. Использует только `published_facts`; вариация — заранее
  утверждённые `variant_values`, допустимые пропуски `omissible` (состояние `known → unknown`,
  никогда не выдумывает `none`/`not_applicable`), порядок полей. Состояния
  `unknown/none/not_applicable` никогда не получают значение. Параметры вариации и seed
  сохраняются в `CardGeneration.variation_params`/`seed` для воспроизведения (D-003).
- `generate_card_with_llm()` — опциональный путь через порт `LLMProvider`/`FaultInjector`
  (6.5.5): переформулировка только поля `description`, выход валидируется (`_validate_description`)
  на отсутствие чисел вне опубликованных фактов; отказ модели, тайм-аут, переполнение,
  невалидный/пустой выход или выдуманное число — откат к детерминированной карточке (C-04),
  режим фиксируется в `variation_params["description_mode"]`.

**Генерация черновика сценария** (`ai/src/dds_ai/scenarios/draft_generation.py`):
- `generate_draft()` — вход: тип происшествия, локация, сложность, тема, профиль ДДС,
  ожидаемое решение диспетчера; опционально `KnowledgeIndex` (6.10) для ссылок на фрагменты.
  Выход — `ScenarioDraftRecord` со статусом `draft`: полный `Scenario` (карточка руководителя,
  проверяемые элементы доклада на все пять `ReportElement`, выключенный канал оператора 112,
  эталон). Число пострадавших без явного указания — `unknown` (инвариант 3, генератор не
  придумывает факты). Базовая реализация — детерминированный шаблон (`template_version`,
  `model_ref=None`); фрагменты из `KnowledgeIndex.search()` только записываются в
  `GenerationMeta.used_fragment_ids`/`corpus_version`, не становятся новыми фактами.

**Структурированный эталон** (`ai/src/dds_ai/scenarios/reference_generation.py`):
- `generate_reference()` — вход: `Scenario` + `Rubric` (+ опционально использованные
  `KnowledgeFragment`), выход — новая версия `ScenarioReference` с `criteria_links`: каждый
  критерий рубрики получает `group_id`, понятное обоснование и ссылки на использованные
  фрагменты. `expected_decision`/`expected_fields`/`not_applicable_criteria` не изменяются
  (решение автора черновика, не этого генератора). `routing.services` — обоснование прямо
  указывает, что маршрут подставляется из движка правил (D-016), не генерируется здесь.
  Детерминирован при одинаковых входах → воспроизводится из сохранённых версий (сценарий,
  рубрика, seed фрагментов не нужен — фрагменты передаются явно).

**Жизненный цикл и gate C-03** (`ai/src/dds_ai/scenarios/lifecycle.py`):
- `submit_for_review()` → `approve()` → `publish()` → `archive()`; `validate_structure()`
  (проверка структуры/фактов при отправке на проверку); `revise()` (комментарий преподавателя
  создаёт новый черновик, требует новую версию `scenario.scenario`, `revises` ссылается на
  предыдущую версию, исходная запись не изменяется — C-09); `assert_assignable()` (черновик
  нельзя назначить, только `published`).
- `check_publish_gate(scenario, routing_decision)` — C-03: если `routing.services` уже не
  входит в применимые критерии сценария (`not_applicable_criteria`), маршрут для него не
  «обязательный», gate не применяется независимо от статуса правила (это покрывает случай
  `syn-003`/`syn-008`, где служба не вызывается вовсе из-за решения «отказать» — причина
  неприменимости не связана с неподтверждённостью маршрута). Иначе маршрут обязателен и
  оценивается автоматически: правило должно быть `active`, иначе публикация обычного сценария
  блокируется; диагностический сценарий (`Scenario.diagnostic`) без такой явной неприменимости
  блокируется тем же путём — флаг сам по себе гарантий не даёт. Вызывается на шаге `publish()`,
  то есть после `approve()`: утверждение преподавателя это не обходит.

**Матрица покрытия** (`ai/src/dds_ai/scenarios/coverage.py`, `docs/ai/coverage-matrix.md`):
- `coverage_cells()` строит ячейки (решение × профиль ДДС × состояние вызова) из живого набора
  сценариев; документ сверяется тестом, чтобы не разойтись с кодом при добавлении сценария.

**Синтетический набор** (`ai/data/synthetic/`) — расширен с 3 (M1) до 9 сценариев:
3 условных профиля ДДС (`dds-center`, `dds-north`, `dds-river`), все три решения диспетчера,
типичные состояния связи (занято/не отвечает/обрыв) и один диагностический сценарий C-03
(`syn-006-unclassified-diagnostic`, тип `unclassified_odor` без правила маршрутизации).
Существующие 3 файла узла A дополнены полем `dds_profile` (совместимо, значение по умолчанию
не требовалось благодаря дефолту в контракте, но проставлено явно). Два новых сценария
(`syn-004`, `syn-007`) используют `variant_values`/`omissible`, чтобы вариация карточки была
проверена не только в unit-тестах, но и на «настоящих» данных набора.

## 4. Что не проверено и почему

- **Защита от выдуманных фактов в `generate_card_with_llm` — только числовая.**
  `_validate_description` ловит числа вне опубликованных фактов (покрывает основной кейс
  инварианта 5 — «нет выдуманных чисел»/«неизвестное не отвечают числом»), но не ловит
  текстовые галлюцинации без цифр (например, придуманное название службы или ложное
  обстоятельство словами). Полная семантическая проверка выхода LLM (факты вне контекста,
  адреса) — по прототипу узла A (`supervisor/phrasing.py::validate_reply`) для реплик
  руководителя, здесь не переиспользована, т.к. карточка — не диалоговая реплика; для M5
  (семантический оцениватель) может понадобиться общий валидатор.
- **`generate_draft()` не использует LLM.** Только детерминированный шаблон (6.5.5 допускает
  это как базовую реализацию); LLM-обогащение описания черновика (аналогично карточке) не
  реализовано — сочтено вне обязательного минимума M4b, т.к. явно протестированное требование
  «враждебный факт → отклонено» сформулировано именно про карточку, не про черновик.
- **Реальные 96 билетов (D-050) недоступны** — весь синтетический набор и все черновики,
  которые может произвести `generate_draft()`, помечены `provenance: "synthetic"`; путь для
  билетов (`Provenance.TICKET`, обязательный `source_ref`) в контракте есть, но генератор его
  не производит — заказчик не предоставил исходники (см. системное напоминание задачи).
- **Профили ДДС (`dds_profile`) — рабочее решение команды**, не ответ на Q03/D-019. Названия
  (`dds-center`/`dds-north`/`dds-river`) придуманы для демонстрации покрытия по трём условным
  группам, не соответствуют реальным приоритетным ДДС пилота.
- **Матрица покрытия — не полная.** Один диагностический сценарий на весь набор; несколько
  явных пробелов перечислены текстом в `docs/ai/coverage-matrix.md` (раздел 1), не устранялись
  в рамках этой вехи (не входило в обязательный диапазон 8–12).
- **Локационные паттерны генератора черновика (`_location_pattern`) — эвристика.** Разбирает
  улицу/дом по маркерам («ул.», «пр.», «д.») тем же способом, что и вручную написанные
  синтетические сценарии, но не тестировалась на реальных адресах вне синтетики (адресный
  справочник D-013 не подключён).
- **Интеграция с полным циклом (`cycle/session.py`, узел A).** Новые сценарии (`syn-004`...
  `syn-009`) не добавлены в `TableRoutingEngine` мока `cycle/session.py::synthetic_routing()` —
  они валидны как контракт и покрыты тестами уровня `scenarios/`, но сквозной прогон
  `TrainingSession` (карточка → решение → звонок → оценка) проверялся узлом A только на
  исходных трёх сценариях. Файл `cycle/session.py` не менялся (вне области узла, использует
  `mocks/operator112.py`, не новый генератор), чтобы не пересекаться с узлом D.
- **`mocks/operator112.py` не заменён нигде.** `cycle/session.py` продолжает использовать
  старую тривиальную генерацию (`seed=0`, без вариации) из M1 — замена на
  `scenarios/card_generation.py::generate_card` в реальном цикле попытки не входила в это
  M4b (риск конфликта с узлом D/будущим M5, которые тоже читают `TrainingSession`); это
  оставлено на согласование оркестратора (см. «Вопросы» ниже).

## 5. Решения, принятые по ходу

1. **Gate C-03 смотрит на `not_applicable_criteria`, а не только на флаг `diagnostic`.** Первая
   версия требовала `diagnostic=True` всегда, когда `routing.services` неприменим и маршрут не
   активен — но это ломало уже существующие (узел A) `syn-003`/`syn-008`, где `routing.services`
   неприменим по педагогической причине (решение «отказать»), не из-за неопределённости
   маршрута. Пересмотрено: gate проверяет только случай, когда `routing.services` заявлен как
   применимый критерий, но живой маршрут не подтверждён — именно это и есть «сценарий с
   автоматической оценкой маршрута» по тексту C-03. Флаг `diagnostic` — по-прежнему
   единственный формально предусмотренный маркер учебного сценария на выявление
   неопределённости, но сам gate не завязан на него напрямую; тест
   `test_non_diagnostic_scenario_with_route_already_inapplicable_publishes_regardless_of_rule`
   фиксирует это решение.
2. **Лексический (не семантический) генератор описаний.** И детерминированная, и LLM-вариация
   описания карточки работают на уровне готовых строк (`variant_values`) или узкой валидации
   (числа), а не свободной генерации текста моделью по умолчанию — соответствует 6.5.5
   («базовая реализация детерминированная»ную) и минимизирует поверхность для галлюцинаций.
3. **`ScenarioReference.criteria_links` добавлены как новое поле, а не отдельный контракт.**
   Так публикация «пары `scenario_version` + `reference_version`» естественно остаётся одним
   объектом `Scenario.reference.reference` (уже существовавший `VersionRef` из M1) — не
   понадобился отдельный `ReferenceRecord` с дублирующей версией.
4. **`Scenario.dds_profile` и `Scenario.diagnostic` — поля с дефолтами**, не обязательные:
   контракт остаётся совместимым с уже влитыми сценариями узла A без миграции данных.
5. **Не переиспользован `mocks/operator112.py` в `cycle/session.py`.** Новый генератор карточки
   живёт отдельно (`scenarios/card_generation.py`) и не подключён к сквозному циклу — решение
   явно вынесено в открытые вопросы ниже, а не сделано молча, чтобы не создавать скрытых
   поведенческих изменений в уже проверенном узлом A цикле.
6. Формальные ADR не заводились: стек не менялся (ADR-0001), контракт меняется совместимо без
   смены `CONTRACTS_VERSION` (по прямому указанию задачи узла).

## 6. Риски и вопросы оркестратору

1. **Кто подключает `scenarios/card_generation.py`/`generate_draft`/`generate_reference` к
   реальному циклу попытки и хранилищу?** Сейчас это самостоятельный, покрытый тестами модуль
   без вызывающего кода в `cycle/`. `cycle/session.py` (узел A) по-прежнему создаёт карточку
   через `mocks/operator112.py` без вариации. Нужно решение: заменить вызов в `cycle/session.py`
   (кто это делает — узел A/D или следующий узел F/M5?) или оставить `scenarios/` как API для
   будущего слоя черновиков/публикации у бэкенда (по аналогии с решением M4a — «генераторы
   мокают хранение, не реализуют его»).
2. **`ScenarioDraftRecord` не персистится.** Хранилище черновиков (аналог `CardStore`) не
   описано контрактом — жизненный цикл (`lifecycle.py`) работает на переданном в память объекте
   через `model_copy`. Нужен мок хранилища черновиков, если M5/M6 или бэкенд будут показывать
   очередь черновиков преподавателю; не делал его умозрительно без явного потребителя.
3. **Диагностических сценариев только 1 из 9.** Если оркестратор/M5 (калибровка) считает это
   недостаточным для проверки gate на разных профилях — стоит явно попросить расширение партии,
   а не расширять сейчас без подтверждённой необходимости (риск лишней синтетики без
   потребителя).
4. **Профили ДДС (`dds_profile`) — временное имя команды.** Как только придёт ответ на Q03
   (D-019, приоритетные ДДС пилота), значения нужно будет заменить/сопоставить — сейчас в коде
   нет привязки к реальным подразделениям, только к синтетическим меткам.
5. **Проверка текстовых (не числовых) галлюцинаций LLM-описания карточки не реализована** (см.
   «Что не проверено»). Если M5 будет делать общий валидатор выхода LLM для семантического
   оценивателя — возможно, стоит вынести его в общий модуль и переиспользовать здесь вместо
   текущей узкой проверки чисел.
