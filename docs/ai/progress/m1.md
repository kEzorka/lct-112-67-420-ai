# M1. Руководитель без LLM — 28.09.2026

Ветка `ai/m1-supervisor` (от `main-ul2qoh`). Формат — раздел 13 [`agent-prompt.md`](../agent-prompt.md).

## 1. Что сделано

**Исполнитель адаптеров** — `ai/src/dds_ai/worker/`
- `executor.py`: `AdapterExecutor` на пару (компонент, полоса). Свой пул потоков на каждую пару, лимит параллелизма `max_concurrency`, ограниченная очередь `max_queue`. Переполнение → `ComponentFailure(overflow)`. Тайм-аут считается от постановки в очередь, то есть включает ожидание. Счётчики: выполнено, ошибки, тайм-ауты, переполнения, задержки.
- `service.py`: `InferenceWorker`. Реестр адаптеров. `call()` идёт по цепочке `FaultInjector.call()` → исполнитель, поэтому каждый сбой попадает в журнал. Есть административное отключение компонента, `status()` для администратора (`up / overloaded / down`, `running`, `queue_length`, версия модели) и `preflight()` по `contracts/worker.py`.
- `ai/config/worker.cpu.json`: политики CPU-профиля для всех шести компонентов. Для LLM/STT/TTS задана полоса `interactive`, для фоновых задач — `background`. Значения рабочие, до замера.

**Контракт сценария** — `ai/src/dds_ai/contracts/scenario.py`, схема `contracts/scenario.schema.json`
- `Scenario` содержит опубликованные факты карточки, собеседников (`InterlocutorBrief`) и скрытый эталон `ScenarioReference`.
- `InterlocutorBrief` — контракт собеседника по D-030. В нём `Interlocutor` (`role_id`, разрешённые действия), факты собеседника, проверяемые элементы доклада (суть, место, обстоятельства, решение ДДС, запрос), сценарные исходы вызова (`busy / no_answer`, обрыв после N реплик) и флаг `enabled`: голосовой канал оператора 112 выключен.
- Проверки контракта:
  - у синтетического сценария заголовок начинается с «СИНТЕТИКА», а `source_ref` пустой; у билета `source_ref` обязателен;
  - у факта в состоянии «неизвестно / нет / не применимо» нет значения;
  - элементы доклада покрывают все пять проверяемых элементов.
- Синтетический набор `ai/data/synthetic/` (есть README): три сценария, по одному на каждое решение ДДС (ответить, перенаправить, отказаться). В них есть «занято», «не отвечает», обрыв связи и выключенный канал 112.

**ИИ-руководитель без LLM** — `ai/src/dds_ai/supervisor/`
- `dialogue.py`: конечный автомат `слушать → уточнить → повторить понятое → подтвердить`, фазы `listening / awaiting_confirmation / confirmed / ended`.
  - Уточнений не больше двух на элемент, поэтому автомат не зацикливается.
  - Руководитель получает только `InterlocutorBrief`, эталона у него нет.
  - Повтор понятого состоит только из фраз самого обучаемого.
  - Ответы на вопросы берутся только из фактов собеседника. Неизвестный факт → «неизвестно».
- `templates.py` + `ai/config/supervisor.fallback.ru.json`: версионированный шаблон, единственный генератор реплик на M1 (режим `fallback`). В шаблон можно подставить только `{items}`, `{label}` и `{value}`; это проверяется при загрузке. Каждая реплика несёт `model_ref`: версию шаблона и версию сценария.
- `matching.py`: правила M1 — основы слов, числа как целое слово, маркер `слово$` для точного совпадения. Здесь же классы реплик: инъекция, вопрос, «да», «нет».
- `phrasing.py`: шов для M3. `validate_reply()` проверяет длину и не пускает числа вне контекста; проверка применяется и к шаблонным репликам. `LLMPhraser` ходит в полосу `interactive` через воркер. Любой сбой или невалидный выход → шаблонная реплика, а сбой пишется в `Turn.failures`.
- `ack.py`: `summarize_acks()` считает засчитанные подтверждения C-05 по журналу событий.

**Сквозной цикл** — `ai/src/dds_ai/cycle/`
- `session.py`: `TrainingSession` проходит уведомление → карточку → правки → решение → набор номера → разговор → подтверждение → сдачу → оценку через `mocks/scoring.py`.
  - Текстовый канал: `text_delivered` несёт `ack_id`.
  - Голосовой канал на моках: TTS-заглушка вызывается через воркер, воспроизведение — `MockMediaTransport`, события `ack.*`.
  - Сдача с пропусками возможна только с явным `incomplete=True` (C-02).
- `rules.py`: детерминированные проверки 10 из 13 критериев рубрики по журналу событий (C-01, C-02, C-05). Три семантических критерия проверяет оцениватель через фоновую полосу. Без оценивателя они получают `not_checked`.
- Новые моки: `mocks/event_log.py` (журнал с серверными `seq`/`server_ts`, управляемые часы) и `mocks/operator112.py` (карточка только из опубликованных фактов).

**Совместимые дополнения контрактов.** Поля не удалялись и не переименовывались, `CONTRACTS_VERSION` не менялся:
- событие `scenario_call_state` (`busy / no_answer / dropped`, `role_id`, `call_id` может быть пустым в текстовом режиме);
- `SubmitAccepted.incomplete`, `SubmitAccepted.missing_steps` (C-02);
- `TextDelivered.ack_id` (C-05, текстовый режим);
- `ComponentStatus.lane`, `ComponentStatus.running`;
- `FaultInjector.fault_for()`;
- параметр `worker=` у `judge_criterion()`.

Не проводились: на M1 нет моделей. Задержки в тестах — только проверка порядка величин (< 0,5–1 с), это не замер производительности.

## 4. Что не проверено и почему

- **Настоящие модели и задержки.** Нет STT/TTS/LLM (M2–M3). Значения в `worker.cpu.json` не замерены.
- **Зависшую модель нельзя прервать.** Исполнитель построен на потоках. После тайм-аута вызов снимается с ожидания, но поток продолжает занимать слот параллелизма до возврата; это видно в `running`. Для настоящего прерывания нужна изоляция процессом — решается вместе с runtime моделей (M2/M3).
- **Метрики.** Они доступны только в памяти (`ExecutorMetrics`, `status()`). Транспорта для администратора нет: протокол не выбран (B03).
- **Профиль `gpu`.** Конфигурации нет, потому что нет замера.
- **Неуверенность STT по критической сущности → переспрос.** Нужен вход с confidence от STT (M2).
- **Сопоставление доклада по ключевым словам.**
  - Отрицания не учитываются: «пострадавших нет» совпадёт с «пострадав».
  - Перефразирования вне шаблонов не распознаются.
  - Поэтому при частичном совпадении `voice.facts_transferred` получает `not_checked`, а не 0: правила M1 не доказывают отсутствие сведений. Окончательную проверку делает семантический оцениватель (M5).
- **`card.address` при несовпадении** получает `not_checked`. Отличить «неполный адрес» (0,5) от «неверного» (критическая ошибка W-01) правило M1 не умеет — нужно структурное сравнение (M5).
- **Семантические критерии** (`card.circumstances`, `manual.*`) проверены только с оценивателем-заглушкой.
- **C-01 не полностью.** Перезагрузка, пауза, mute/hold в raw time и экспертная проверка нетаймингового критерия не проверялись. Проверены 20/170, опоздание 35 с и порог 181 с.
- **Голосовой канал — только мок.** Реплика ученика подаётся готовым текстом, без STT. Воспроизведение — `MockMediaTransport`. Настоящий медиатракт у бэкенда.
- **LLM-формулировка.** `LLMPhraser` — минимальный шов для проверки fallback. Полноценный валидатор (факты вне контекста, адреса, схема ответа) и защита от инструкций на уровне промпта — M3.

## 5. Решения, принятые по ходу

ADR не заводились: стек не менялся (ADR-0001). Рабочие решения:

1. **Ответ руководителя на вопрос о факте — действие `listen`.** Среди четырёх действий 6.4 нет отдельного «ответить». Новое значение enum не добавлялось.
2. **В текстовом режиме голосовые критерии `voice.*` получают `not_checked`**, итог предварительный (C-04: «голосовой навык не подтверждается»). Если разговора не было совсем, это `not_done` в любом режиме (C-02).
3. **Технический сбой делает критерий подтверждения `technical_error`**, а не `failed`. Это относится к недоставке ack из-за TTS или медиа и к обрыву не по воле ученика. Так «голосовой критерий не пройден» по C-05 не становится ошибкой ученика (инвариант 4). Сброс учеником до подтверждения → `not_done`.
4. **Слышимым считается вызов в состоянии `active` или `muted`; `hold` — нет.**
5. **Любой `model_failure` в попытке — флаг технического нарушения C-01**: время → `technical_error`. Это относится и к отказу LLM, закрытому fallback: C-04 говорит «любой сбой после старта».
6. **Вопрос и инъекция не засчитываются как переданные сведения** — ни в автомате, ни в правиле оценки.
7. **Сценарный обрыв (`drop_after_turns`) действует только на первое соединение.** Повторный звонок начинает доклад заново.

## 6. Риски и вопросы

### Вопросы оркестратору

1. **Дополнения контрактов для бэкенда (B04).**
   - Новые поля: событие `scenario_call_state`, `SubmitAccepted.incomplete/missing_steps`, `TextDelivered.ack_id`, `ComponentStatus.lane/running`, схема `scenario`.
   - Все дополнения совместимые, но меняют JSON Schema. Нужно решение, повышать ли `CONTRACTS_VERSION`, и согласование с владельцем журнала событий.
2. **Словарь причин `ack.delivery_unconfirmed`.** Сейчас это свободная строка. Код различает только `call_ended_by_client` (действие ученика) и остальные причины (технические). Мок медиатракта пишет `call_dropped` и `client_silent`, воркер — `tts_failed`. Предлагаю enum в контракте, но это касается владельца медиатракта.
3. **Решение 2 (текстовый режим → `not_checked`)** нужно подтвердить. Альтернативы: `technical_error` (если текстовый режим включён из-за сбоя) или `not_applicable` (если текстовый режим назначен до старта). От выбора зависит, будет ли текстовая попытка когда-нибудь окончательной.
4. **Решение 5** нужно подтвердить: должен ли сбой LLM, полностью закрытый шаблонным fallback, исключать попытку из сопоставимого рейтинга.
5. **Решение 4 (`hold` не слышим)** требует подтверждения от владельца медиатракта.

### Риски

- Правила ключевых слов в сценариях пишутся руками и хрупкие. До M5 это даёт `not_checked` там, где оцениватель, возможно, поставил бы балл. Предварительных итогов будет больше.
- Узлы B (voice) и C (knowledge/nlp) могут менять те же общие контракты. Возможные конфликты при слиянии: `contracts/events.py`, `contracts/worker.py`, `contracts/__init__.py`, `contracts/*.schema.json`.
