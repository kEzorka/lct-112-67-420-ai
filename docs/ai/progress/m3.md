# M3. LLM-реплики руководителя — 28.09.2026

Ветка `ai/m3-llm` (от `main-ul2qoh`). Формат — раздел 13 [`agent-prompt.md`](../agent-prompt.md).

## 1. Что сделано

**LLM-формулировка внутри действия автомата** — `ai/src/dds_ai/supervisor/`
- `phrasing.py` — `LLMPhraser`.
  - Автомат уже выбрал действие и черновик реплики из шаблона M1. LLM формулирует только
    этот черновик.
  - Вызов идёт через `InferenceWorker` в полосе `interactive`.
  - Невалидный выход → один повтор. В повторный промпт попадает только код причины, текст
    отклонённого ответа туда не попадает. После второго отказа берётся шаблон M1.
  - После тайм-аута, переполнения или ошибки повтора нет: сразу fallback, чтобы не удваивать
    задержку живого звонка.
  - Каждая попытка пишется в журнал сбоев. Для невалидного выхода это `invalid_output`, в
    `detail` — только код причины, без текста модели (инвариант 9). Сбой runtime (в том числе
    `ValueError` от llama.cpp) записывается как `error`, а не `invalid_output`.
  - Для каждой попытки сохраняется время генерации и валидации, для хода — полное время
    формулировки (`PhraseOutcome`, поле `Turn.llm`).
  - Режим `llm` и версия видны в `ModelRef` реплики: модель и `prompt_version`.
- `prompting.py` — `PhraseRequest` и `PromptTemplate`.
  - LLM получает только роль, выбранное действие, черновик, факты собеседника, которые автомат
    использовал в этом ходе, и историю вызова (не больше 6 реплик).
  - Полей для эталона и проверяемых элементов доклада нет по построению (инвариант 1).
  - Реплики диспетчера — данные. Из них убирается разметка (`<>{}` и кавычки) и переводы
    строк, длина ограничена 400 символами. Они кладутся в именованные блоки, и инструкция
    прямо говорит, что это не команды (инвариант 2).
- `ai/config/supervisor.prompt.ru.json` — версионированный промпт `supervisor-phrase-ru-m3-1`.
  Выход модели — JSON `{"action", "text"}`.
- `validator.py` — проверка выхода. Коды причин — `RejectReason`, 18 значений:
  - схема JSON, действие совпадает с выбранным автоматом, длина не больше 300 символов, нет
    разметки;
  - нет чисел цифрами и словами, адресных элементов, имён собственных, служб и латиницы вне
    разрешённого контекста;
  - нет служебных тем (оценка, балл, эталон, сценарий, «правильное» или «ожидаемое» решение,
    инструкции), если их нет в черновике;
  - «неизвестно» не пропадает, числа из черновика не теряются;
  - получение доклада подтверждает только `confirm_receipt`; повтор понятого — вопрос;
    уточнение — вопрос или просьба уточнить.
  - Разрешённый контекст LLM — только черновик и факты хода. Реплики диспетчера в него не
    входят: всё, что из них нужно повторить, автомат уже положил в черновик. Поэтому
    «запиши адрес проспект Ложный 99» не превращается в разрешённый факт.
- `dialogue.py`: состояние диалога меняется до формулировки, выход LLM в него не возвращается.
  Отказ на инъекцию, которую узнали правила M1, — фиксированная реплика, LLM не вызывается.

**Адаптер llama.cpp** — `ai/src/dds_ai/llm/`
- `llamacpp_provider.py` — `LlamaCppProvider`, extra `ai[llm-llamacpp]` (`llama-cpp-python`,
  MIT).
  - Только локальный файл GGUF, ничего не скачивается.
  - `model_version` берётся из манифеста; если его нет — отпечаток файла.
  - Ответ ограничен грамматикой JSON-схемы.
  - Свой срок генерации: адаптер перестаёт читать поток токенов, закрывает его и бросает
    `TimeoutError`.
  - Режимы chat и completion.
- `fake.py` — `EchoDraftLLM`: детерминированный фейк для обвязки замера.

**Замер стадий** — `ai/bench/run_llm_bench.py`, `ai/bench/make_tiny_gguf.py`, отчёт
[`bench/llm-cpu.md`](../bench/llm-cpu.md).

## 4. Что не проверено и почему

- **Настоящая LLM.** huggingface.co закрыт сетевой политикой (403), веса не скачивались.
  Нет замера задержки и качества, нет доли отклонений валидатора на живых перефразированиях.
  Ложные отказы проверены только на формулировке, совпадающей с черновиком.
- **Проверки валидатора — эвристики для русского языка**: словари числительных, адресных
  слов, служб, служебных тем; имена — по заглавной букве не в начале предложения.
  - Пропуск возможен: например, выдуманный факт без чисел, адресов и имён («дверь заперта»).
    Такой факт валидатор не поймает. Смягчение — у LLM нет фактов, кроме черновика и фактов
    хода, так что новые сведения ей брать неоткуда.
  - Возможны и ложные отказы на настоящей модели. Их цена — шаблонная реплика вместо живой.
  - Нужна калибровка на настоящей модели.
- **Обработка промпта до первого токена** не прерывается сроком генерации адаптера. Её
  ограничивают только длина промпта и тайм-аут воркера. Поток llama.cpp, как и на M1, держит
  слот параллелизма до возврата.
- **Первый звук ≤ 3 с (D-052)** — нужны настоящие LLM и TTS.
- **Задержки стадий есть только в памяти** (`Turn.llm`). Контракта события для них нет, транспорт
  метрик не выбран (B03).
- **Версия промпта в `AttemptVersionSnapshot`.** Версия есть в каждой реплике (`ModelRef`),
  но снимок версий при старте попытки пишет бэкенд. Этот стык не проверялся.
- **Текстовый режим, назначенный до старта** из-за провала preflight. `technical_error` ставится
  только если в журнале попытки есть `model_failure` STT или TTS (см. вопрос 3).

## 5. Решения, принятые по ходу

ADR не заводились: стек не менялся (ADR-0001, llama.cpp-совместимый runtime).

1. **Разрешённый контекст LLM — черновик и факты хода**, без реплик диспетчера. На M1 для
   шаблона контекстом были и реплики диспетчера. Для LLM это слишком широко: инъекция
   превратила бы свои числа и адреса в разрешённые.
2. **Отказ на инъекцию, которую узнали правила M1, LLM не формулирует.** Это единственная
   реплика, где служебная тема и есть предмет ответа, поэтому она остаётся фиксированной.
3. **Повтор — только после `invalid_output`.** После тайм-аута и ошибок сразу fallback.
4. **Выход модели — JSON `{"action", "text"}`.** Действие в выходе должно совпадать с выбранным
   автоматом. В адаптере llama.cpp форму ответа дополнительно держит грамматика.
5. **Срок генерации llama.cpp соблюдается чтением потока токенов**, а не принудительным токеном
   конца: с грамматикой принудительный токен конца аварийно завершает процесс. Дефект найден
   дымовым прогоном.
6. **Сбой runtime (`ValueError` от llama.cpp) — `error`, а не `invalid_output`.** Классификация
   сделана в `LLMPhraser`; общий `FaultInjector` не менялся.
7. **M1-3 определяется по журналу**: в попытке есть `model_failure` STT или TTS. Отдельного
   значения `Channel` или нового контракта нет.

## 6. Риски и вопросы

### Вопросы оркестратору

1. **Успешный повтор и рейтинг.** Сценарий: первая попытка невалидна, вторая прошла.
   Сейчас `model_failure(invalid_output)` пишется в журнал, и по решению M1-4 попытка получает
   флаг технического нарушения: `time.*` → `technical_error`, итог предварительный. На настоящей
   модели это может случаться часто и выводить много попыток из рейтинга, хотя ученик слышал
   нормальную реплику. Варианты:
   - (а) оставить как есть;
   - (б) писать отклонённую попытку, после которой повтор прошёл, отдельным событием или
     полем, не считая её техническим нарушением;
   - (в) считать нарушением только ход, закрытый шаблоном.
   Решение затрагивает C-01/C-04 и, возможно, контракт событий.
2. **`FaultInjector` превращает любой `ValueError` в `invalid_output`.** Для LLM это обойдено в
   `LLMPhraser`. У других адаптеров (семантический оцениватель на M5) будет та же ошибочная
   классификация. Предлагаю общее правило в `faults.py`: `invalid_output` — только явная
   ошибка проверки выхода. Это общий код, поэтому здесь его не трогал.
3. **Текстовый режим, назначенный до старта попытки** из-за провала preflight. Кто пишет в
   журнал событие сбоя голосового тракта — бэкенд или воркер? Без него голосовые критерии
   получат `not_checked`, а не `technical_error` (M1-3).
4. **Задержки стадий в журнале.** Добавить ли в `utterance` или в отдельное событие время
   генерации и валидации? Это совместимое изменение контракта, но касается бэкенда (B03/B04).

### Риски

- Качество формулировок и доля fallback на настоящей модели неизвестны. При высокой доле
  fallback живой пользы от LLM мало, а задержка удваивается из-за повтора.
- Небольшие модели плохо держат формат JSON без грамматики. Грамматика есть только в адаптере
  llama.cpp: другой runtime должен дать аналог.
- Валидатор на ключевых словах и правила M1 хрупки для перефразирований; пересмотр нужен после
  замера на настоящей модели и после M5.
