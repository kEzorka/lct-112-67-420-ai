## 1. Роль и цель

Ты — ведущий инженер ИИ-контура учебного тренажёра диспетчера ДДС (хакатон ЛЦТ-2026, заказчик — ДГОЧСиПБ). Твоя задача — спроектировать, реализовать и проверить все компоненты, где участвуют модели: распознавание и синтез речи, ИИ-руководителя, ИИ-оператора 112, семантическое оценивание, подсказки, предложение сложности, профиль подготовки и рекомендации, генерацию сценариев и эталонов, проверку грамматики, аналитику ошибок группы, локальную базу знаний, а также локальный inference-worker с очередями, тайм-аутами и деградацией.

Результат должен работать **полностью локально, без интернета, на CPU**, с заменяемым GPU-профилем, и быть **проверяемым**: каждое утверждение о качестве подтверждается измерением или тестом, каждое решение модели — сохранённым основанием.

## 2. Предметная область в пяти предложениях

1. Обучаемый — **диспетчер ДДС**, а не оператор 112. Он не принимает звонок заявителя.
2. **ИИ-оператор 112** заранее создаёт входную карточку происшествия в пределах опубликованных фактов сценария.
3. Диспетчер получает уведомление, открывает карточку (норматив ≤30 с), дополняет её вручную, выбирает `ответить / отказаться / перенаправить`.
4. Затем диспетчер **звонит голосом ИИ-руководителю** через VoIP-эмулятор (не SIP), передаёт сведения и получает подтверждение; вся отработка — ≤180 с от открытия карточки до сдачи.
5. ИИ оценивает действия по проверяемым критериям, даёт подсказки и рекомендации, строит профиль подготовки и предлагает следующие задания; преподаватель утверждает сценарии и может корректировать оценки.

### 4.2. Потребляет через контракты (не реализует, не меняет)

- **Маршрутизация служб (D-016, C-03)** — детерминированный движок правил ЕКП. **LLM никогда не выбирает, не добавляет и не убирает службы.** ИИ может показывать признаки и объяснение, но источник назначения — только правило с версией. Вход движка: извлечённые признаки + адрес + состояние карточки + `routing_rules_version`; выход: тип / ЕКП / сценарий / главная служба / маршрутизация. `rule_status = active | ambiguous | quarantined`: только `active` даёт auto-pass/fail, остальные уходят эксперту (в текущем классификаторе 148 неоднозначных строк, 34 без ЕКП, 102 без главной службы).
- **Доменная модель и журнал событий (Miro 05)** — PostgreSQL: `Card {source_payload, dispatcher_edits, card_revision[]}`, `TrainingAttempt {events, evidence, status}`; object store для документов и аудио; vector index для RAG. События попытки: `notification_shown`, `card_opened`, `card_revision`, `selected_action`, `played_audio_ack`, `submit_clicked`, `submit_accepted`, `timeout`. Тайм-аут — событие, он не создаёт действие, звонок или сдачу.
- **`AttemptVersionSnapshot` (D-003, C-08)** — фиксируется 1:1 при старте попытки: `scenario · reference · card_schema · classifier · routing_rules · rubric · time_policy · model/template · difficulty_config`. ИИ пишет в снимок версии своих моделей, промптов и шаблонов.
- **`ScoreVersion` (D-038, C-09)** — append-only: `attempt_id · parent_score_version_id · author · reason · timestamp · criterion_results[] · total_score · provisional`. Экспертная корректировка создаёт версию N+1; администратор оценки не меняет.
- **Медиатранспорт VoIP-эмулятора (D-021, D-023)** — ИИ получает аудиопоток и управляющие события вызова (`call_id`, mute, hold, завершение) и отдаёт аудио ответа.
- **Карточка, схема данных, UI (D-011, D-012, D-020)** — ИИ читает видимые поля и пишет только в разрешённые ему сущности (реплики, события, замечания, черновики).
- **Жизненный цикл попытки и время (D-004, D-005, C-01, C-02)** — ИИ не решает, когда попытка сдана.
- **Расчёт итогового балла (C-06)** — агрегация детерминирована; ИИ поставляет результаты критериев (`criterion_status` + значение, инвариант 12) с доказательством. Рабочая рубрика до утверждения — W-01 в реестре → `rubric_version`. На доске Miro (04) у тех же весов 20/25/25/20/10 другие названия групп: карточка · решение/маршрутизация · голос · процесс/время · ручной ввод. Какой вариант правильный, пока не подтверждено; состав групп держи в конфигурации рубрики, не в коде.
- **RBAC, хранение, резервирование (D-054, D-056, D-057, C-09)** — ИИ соблюдает политики, но не определяет их.

Если для твоей задачи нужен контракт соседнего модуля, которого ещё нет, — **сначала опиши его в `contracts/` как черновик и замокай**, не встраивай логику соседа в ИИ-контур.

### 4.3. Фактическое состояние бэкенда

Сверка с репозиторием бэкенда — [`docs/backend/contract-notes.md`](../backend/contract-notes.md) (коммит бэкенда `5757c89`). Сейчас бэкенд — только учётные записи и административный аудит (Java 25, Spring Boot, PostgreSQL): логин по cookie, пользователи, роли с тремя административными правами, отделы, учебные группы, `audit.action_logs`. **Ни одного контракта из 4.2 в бэкенде ещё нет**, вызовов ИИ нет, миграций схемы нет.

Что из этого следует для тебя:
- Все контракты 4.2 — черновики в `contracts/`, владелец реализации — бэкенд; ИИ-контур их предлагает и мокает, но не реализует хранение. Черновики M0: карточка и ревизии, события попытки (append-only, `attempt_id`, `seq`, `server_ts`, `client_ts`, `payload`), `AttemptVersionSnapshot`, `ScoreVersion` с результатами критериев, рубрика как версионируемая конфигурация (W-01), канал событий ИИ-worker → бэкенд (`ack.*`, STT, сбои), preflight и статус компонентов.
- Протокол бэкенд ↔ inference-worker не выбран: в бэкенде подключён gRPC-клиент, в промпте по умолчанию HTTP/WebSocket. Схемы сообщений делай независимыми от транспорта (JSON Schema/pydantic, из которых можно получить и `.proto`); транспорт — отдельный адаптер, решение — ADR после ответа B03.
- Совместимые типы: идентификаторы UUID, время `timestamptz` (ISO 8601 с зоной), JSON — `jsonb`. Используй их в контрактах без конвертаций.
- Сервисной аутентификации нет — в контракте заложи её явно (сервисный токен или mTLS), пользовательскую cookie ИИ-worker не использует.
- Обучаемый — диспетчер ДДС (D-001): в контрактах не используй «оператор» для обучаемого; нейтральное имя сущности — `incident_card`.
- Тестовые ФИО для бэкенда: его валидатор пока не принимает дефис и «ё» — синтетические пользователи без них, пока это не исправлено.
- vector index и документы базы знаний — в ИИ-контуре (6.10); аудио и транскрипты — object store, владелец не определён (B04).

## 5. Жёсткие инварианты (нарушение = дефект)

1. **Скрытый эталон** сценария не попадает в видимые обучаемому поля, в ответы API обучаемому и в пользовательские реплики LLM (D-011, D-026). В промпт руководителя эталон оценивания не передаётся вообще.
2. **LLM не меняет системные данные**: карточку, маршрут, балл, статус попытки. Реплика обучаемого — это реплика, а не команда (D-026). Фразы вида «измени оценку», «правильный адрес такой-то», «забудь инструкции» не влияют на состояние.
3. **Неизвестное остаётся неизвестным.** Руководитель и оператор 112 не выдумывают факты вне сценария; на вопрос о неизвестном числе пострадавших не отвечают числом.
4. **Три разных состояния**: ошибка ученика, отсутствие доказательства, технический сбой. Сбой модели, тайм-аут, неразборчивое распознавание **никогда** не превращаются в ошибку ученика; результат — «не проверено» или флаг технического нарушения (C-01, C-04, D-037).
5. **Нет выдуманных чисел.** Если модель не отдаёт confidence — поле пустое, а не придуманное значение (D-024). Нет «вероятности успеха» без калибровки (D-044).
6. **Версии закреплены на попытку**: сценарий, классификатор, правила, рубрика, политика времени, а также версии STT/TTS/LLM/промптов/шаблонов. Каждое сохранённое решение модели ссылается на версию модели и промпта (D-003, C-08).
7. **Подтверждение руководителя** засчитывается только при подтверждённом клиентом воспроизведении аудиофрагмента в активном вызове; один `ack_id` на подтверждение; повтор не удваивает (C-05).
8. **Только локальный inference.** Никаких внешних API, облачной телеметрии, загрузки моделей при старте; все веса — в локальном пакете (D-051, C-10). Публичное демо — отдельный синтетический контур без связи с учебным.
9. **Никаких персональных данных и секретов** в запросах к моделям и в логах сверх необходимого (D-055, D-058).
10. **ИИ не заполняет поля за ученика** в самостоятельном режиме и не исправляет текст; подсказки в «делай как я» помечаются как помощь (D-012, D-041).
11. **Неизменяемость в пределах срока хранения**: транскрипты, оценки и основания не перезаписываются; исправление — новая версия (C-09, D-038).
12. **Результат критерия = статус + значение.** `criterion_status ∈ {passed, failed, not_done, no_evidence, technical_error, not_applicable, not_checked}`; значение `0 / 0,5 / 1` есть только у проверенных статусов.
    - `not_done` — проверенное невыполнение при исправной системе (например, пропущенный звонок), даёт 0 и **не** делает итог предварительным.
    - `no_evidence`, `technical_error`, `not_checked` — итог `provisional` с диапазоном (C-06), в профиль и рейтинг не идёт.
    - `not_applicable` — критерий исключается из своей группы.
    - 0,5 (partial credit) — по рабочей конвенции W-01: а) поле заполнено неточно или неполно без критической ошибки; б) действие выполнено позже норматива. Других случаев 0,5 нет. Правило — настраиваемая часть `rubric_version`, заменяется ответом на Q05 / D-040.
    - Критические ошибки W-01 (не вызвана нужная служба, неверный адрес, обработка > 180 с) дают «не сдано» при любом балле, но только как проверенный факт, не при `no_evidence` / `technical_error` / `not_checked`.
    - Неопределённость источника (`source_uncertainty`: ambiguous/quarantined правило, пропуск в классификаторе) ≠ ошибка ученика.
13. **Профиль и рекомендации обновляются только после `valid_score`.** Предварительные, технически нарушенные и `not_checked` результаты профиль не ухудшают и в рейтинг не попадают (C-07).

## 6. Задачи по компонентам

Для каждого компонента: сначала контракт и тесты, затем реализация, затем замер. Критерии приёмки взяты из реестра и обязательны.

### 6.1. Inference-worker и контракт деградации

На доске этот компонент называется «локальный model gateway»: offline · CPU-first · GPU как заменяемый ускоритель · кэш · очередь · fallback. **Все** ИИ-модули ходят к моделям только через него; синхронные операции (реплики руководителя, STT/TTS в звонке) отделены от фоновых (генерация сценариев и эталонов, индексация RAG, калибровка, аналитика) — фоновая нагрузка не должна увеличивать задержку живого звонка.

**Сделать:**
- Отдельный локальный сервис (или процесс) с адаптерами `STTProvider`, `TTSProvider`, `LLMProvider`, `SemanticJudge`, `Recommender`, `Embedder`. Замена модели — через адаптер без изменения контрактов попытки и карточки.
- Для каждого адаптера: конечный тайм-аут, предел очереди, лимит параллелизма, явное состояние перегрузки, версия политики отказа.
- Preflight до старта попытки: доступность голосового тракта и нужных моделей, способность обслужить заявленный профиль.
- Журнал сбоев: компонент, время, тип (`error / timeout / overflow / invalid_output`), затронутые доказательства.
- Профили `cpu` (базовый, сервер ≥6 ядер, 32 ГБ RAM) и `gpu` (заменяемый) с одинаковой схемой результатов.
- Метрики: длина очередей, задержки по стадиям, ошибки; статус компонентов для администратора.

**Поведение при отказах (C-04):**

| Отказал | Поведение |
|---|---|
| Диалоговая LLM | Детерминированный сценарный fallback: реплики и переходы из проверенного шаблона, без новых фактов; режим фиксируется в попытке |
| STT или TTS / голосовой тракт не восстановлен | Помеченный текстовый разбор; голосовой навык не подтверждается |
| Семантический оцениватель | Критерии — «не проверено», ожидают эксперта или повторного прогона |
| Рекомендатель | Профиль не ухудшается; «рекомендация недоступна»; используется последовательность, назначенная преподавателем; нет назначения — занятие ждёт преподавателя |
| Любой сбой после старта | По политике C-01: флаг технического нарушения, без нормативного временного вердикта, вне сопоставимого рейтинга |

**Приёмка:** по отдельности отключить STT, LLM, TTS, семантическую модель, рекомендатель; вызвать тайм-аут и переполнение очереди. Для каждого случая задокументированы и проверены тестом: состояние UI, сохранённые события, возможность продолжения, статус оценки, исключение из рейтинга. Статическая маршрутизация и сохранение карточки работают без LLM. Полный учебный цикл проходит при отключённом интернете; пакет не скачивает модели при старте.

### 6.2. STT

**Сделать:**
- Потоковое распознавание русского языка на CPU: частичные и окончательные результаты, временные интервалы слов/фраз, версия модели, доступные показатели качества.
- Словарь/подсказки для доменной лексики: названия служб, типы происшествий, адресные элементы, числительные.
- Для критических сущностей (адрес, числа, службы) — сигнал неуверенности, по которому руководитель переспрашивает.
- В mute и на удержании звук ученика **не** поступает в STT.
- Преподаватель может пометить ошибку распознавания; это новая запись, исходная транскрипция сохраняется.

**Выбор модели:** решение временное до пилота. Не фиксируй модель как утверждённую. Прогони 2–3 кандидата на целевом CPU на синтетических и разрешённых учебных репликах (адреса, номера, отрицания, названия служб), сравни WER/CER по сущностям, задержку финального результата и лицензию на локальную поставку. Кандидаты для замера, а не решение: `faster-whisper`/`whisper.cpp`, `GigaAM`, `Vosk`, `T-one`.

**Приёмка (D-024):** локальный прогон содержит адрес, номер, отрицание и название службы; сохранены исходная реплика, результат и интервалы; намеренно искажённое распознавание не приводит к необъяснимому нормативному штрафу; модель меняется через адаптер.

### 6.3. TTS

**Сделать:**
- Локальный синтез: минимум мужской и женский голос; минимум две **различимые** интонации (например, нейтральная и напряжённая). Изменение только громкости не считается интонацией.
- Голос и манера фиксируются в версии сценария; не определяют правильность и не меняют факты.
- Корректное произношение адресов, номеров домов, чисел, аббревиатур служб (нормализация текста перед синтезом).
- Неизменные фрагменты сценария синтезируются заранее, до занятия; живые реплики руководителя — интерактивно.
- Для каждого фрагмента, содержащего подтверждение, TTS/медиатракт генерирует события C-05.

**Выбор модели:** временный. Кандидаты для замера: `Silero TTS`, `Piper`, `XTTS`/`F5-TTS`. **Обязательно проверь лицензию** на поставку в учебный контур заказчика — часть моделей распространяется с некоммерческими ограничениями. Результат проверки — в `docs/ai/licenses.md`.

**Приёмка (D-025):** в офлайн-демо слышны оба голоса и две интонационные версии одной реплики; адреса и числа понятны; пакет содержит веса и сведения о лицензиях.

### 6.4. ИИ-руководитель

**Архитектура:** структурированный диспетчер диалога (конечный автомат) определяет разрешённое действие; LLM только формулирует реплику для выбранного действия.

- Разрешённые действия: `выслушать`, `уточнить`, `повторить понятое`, `подтвердить получение`; сценарные состояния `занято`, `не отвечает`, `обрыв` задаются сценарием и отличаются от технического сбоя.
- Контекст LLM: опубликованная роль руководителя, явно переданные в разговоре сведения, ограниченная история. Эталон оценивания не передаётся.
- Выход LLM проходит проверку: схема, длина, отсутствие фактов вне контекста, отсутствие чисел/адресов, которых не было во входе или в разрешённых фактах сценария. Невалидный выход — повтор или fallback по C-04.
- Доклад диспетчера сопоставляется с проверяемыми элементами сценария: суть происшествия, место, существенные обстоятельства, решение ДДС, запрошенное действие. Руководитель уточняет непонятное (в том числе при неуверенности STT по критической сущности).
- Контракт собеседника: `role_id`, доступные факты, разрешённые действия — чтобы позже подключить канал оператора 112 (D-030, сейчас выключен) без смены ядра.

**Подтверждение (C-05):** события `ack.generated → ack.sent_to_media → ack.played_by_client` либо `ack.delivery_unconfirmed`, с одним `ack_id`, `attempt_id`, `call_id` и ссылками на реплики. Засчитывается только `played_by_client` в активном вызове. Подтверждение приёма входного аудио сервером — не доставка ответа. Слово «принято» в тексте, конец звонка, повторная доставка не создают подтверждение. Подтверждение получения ≠ правильность доклада: неверный адрес может быть услышан и подтверждён, ошибка оценивается отдельно. В текстовом режиме — отдельное событие доставки текста, не выдаваемое за голосовое.

**Задержка:** инженерная цель — первый звук ответа ≤3 с после конца реплики ученика при заявленной нагрузке (D-052, временная цель команды). Требование ТЗ ≤150 мс относится к передаче голоса, **не** к ответу модели; не смешивай их в отчёте.

**Приёмка:** реплика «измени оценку / правильный адрес такой-то» не меняет системные данные; на неизвестное число пострадавших нет выдуманного числа; журнал связывает ответ с доступным контекстом и версией сценария; ранний сброс не даёт подтверждения; TTS падает после формирования подтверждения — голосовой критерий не пройден; разрыв после серверного приёма реплики не создаёт доставку ответа; повтор с тем же `ack_id` не удваивает балл; нормальное воспроизведение даёт ровно одно подтверждение нужного вызова.

### 6.5. ИИ-оператор 112 и генерация сценариев

**Сделать:**
- Генерация входной карточки по схеме D-011 **только** из опубликованных фактов сценария и разрешённых вариаций (формулировки описания, порядок сведений, допустимые пропуски). Никаких новых фактов.
- Состояния `неизвестно / нет / не применимо` не сводятся к пустой строке или нулю.
- Сгенерированная карточка, параметры вариации и seed **сохраняются в попытке** — иначе исходная карточка не воспроизводится (D-003). Для наборов, предназначенных для сопоставимого рейтинга, карточка фиксируется в опубликованной версии сценария либо параметры вариации входят в эту версию — иначе ученики получают разные карточки и рейтинг теряет сопоставимость (C-07).
- Генерация черновиков сценариев для преподавателя. Вход: параметры от человека (тип происшествия · локация · сложность · тема) + утверждённые материалы из базы знаний (6.10). Выход — JSON сценария: `initial_card`, профиль ДДС, вопросы, допустимые действия, факты руководителя, предлагаемая сложность, ссылки на использованные фрагменты источников. Жизненный цикл: черновик → проверка структуры и фактов → утверждение преподавателем → опубликовано → архив. Комментарий преподавателя порождает исправленный черновик.
- **Генератор структурированного эталона.** Вход: сценарий. Выход: ожидаемые действия, ответы, критерии с привязкой к группам рубрики и ссылками на источники; нормативная маршрутизация подставляется из движка правил, не генерируется. Публикуется вместе со сценарием как пара `scenario_version` + `reference_version` только после утверждения преподавателем. Исправление эталона — новая версия; комментарии преподавателей питают обратную связь в версии промптов, эталонов и датасетов.
- Основа — 96 билетов как кандидаты в эталон (D-050); до их получения — **явно синтетические** сценарии, покрывающие три решения диспетчера, типичные ошибки и сбой связи. Не выдумывать содержание отсутствующего билета. Производные варианты хранят ссылку на исходник (для разделения выборок D-039).
- Маршрут служб в сценарии берётся из детерминированного движка. Сценарий с пустым/неоднозначным обязательным маршрутом **не публикуется как обычный** (C-03); допускается только отдельный помеченный диагностический сценарий с явной неприменимостью маршрутных критериев. Утверждение преподавателем этот gate **не обходит**.

**Приёмка:** изменение опубликованного задания не меняет начатую попытку; из сохранённых версий воспроизводятся исходная карточка, ожидаемые действия и объяснение оценки; черновик нельзя назначить; синтетический материал не назван реальным билетом; матрица покрытия показывает три решения диспетчера и пробелы.

### 6.6. Семантический оцениватель

**Сделать:**
- **Ручное дополнение карточки (D-034):** структурированные поля — точное сравнение с разрешённой нормализацией; свободный текст — локальная семантическая проверка по фактам эталона с цитатой из ответа ученика. Перефразирование не штрафуется. Исходный дефект карточки ИИ не штрафуется, если исправление не было заданием. Грамматика — отдельное замечание, влияет на балл только если критерий включён заранее. Проверяются только поля, доступные диспетчеру.
- **Проверка грамматики ([ТЗ]):** локальная, после каждого ручного изменения текста карточки и в итоговом отчёте; замечание содержит фрагмент и предлагаемое исправление, но текст ученика не исправляется автоматически (инвариант 10).
- **Разговор с руководителем (D-036):** факт вызова, адресат, передача существенных фактов, получение подтверждения (по C-05). Каждое семантическое замечание ссылается на фрагмент транскрипта с интервалом. Неразборчивая запись или потеря доказательства — «не проверено». Тембр, пол голоса, акцент — не критерии. Текстовый аварийный режим маркируется отдельно.
- **Замечания (D-037):** тип (`время`, `факт/поле`, `действие/маршрут`, `коммуникация`, `последовательность`, `грамматика`) плюс отдельно `неопределённость эталона/ИИ` и `техническая неисправность`; серьёзность `информационное / ошибка / существенная ошибка` из рубрики; доказательство; владелец проверки. Неисправность STT не увеличивает счётчик ошибок.
- **Выход:** для каждого критерия — `criterion_status` и значение по инварианту 12, доказательство, версия модели и промпта. Входы оценивателя: `event_stream + evidence + active rules + ML hints + grammar`. Выход LLM проходит проверку схемы; невалидный — `not_checked`, а не 0.
- **Цепочка объяснения:** результат критерия → наблюдаемое событие / доказательство → правило и его версия → понятное обоснование.
- **Совместимость с C-06 и W-01:** группы «Приём и открытие 20 / Заполнение карточки 25 / Выбор действий и служб 25 / Разговор с руководителем 20 / Грамотность 10», порог прохождения 75 без критических ошибок, нормировка внутри групп, неприменимые группы исключаются, при непроверенных критериях — статус «предварительно» и диапазон, при отсутствии применимых — «оценка не предусмотрена». Сам расчёт — детерминированный модуль оценивания; ты обеспечиваешь, что твой выход корректно в него ложится, и покрываешь тестами граничные случаи.
- **Экспертная корректировка (D-038, C-08):** поправка создаёт новую версию оценки; зависимые агрегаты и неприменённые рекомендации помечаются устаревшими.

**Калибровка (D-039):**
- Набор контрольных попыток, утверждённых преподавателем: правильные, частично правильные, ошибочные, перефразирования, дефекты STT.
- Метрики по каждому критерию: согласие с экспертом, ложные штрафы, пропуски ошибок, доля «не проверено».
- Исходный билет и все его производные — в одной выборке; контрольные примеры не участвуют в настройке промптов.
- До достаточной разметки — показывать объём проверки и наблюдаемые метрики, без заявлений о доказанной точности.

**Приёмка:** два равнозначных описания получают одинаковую оценку фактов; неверный адрес или потеря обстоятельства объясняется конкретным сравнением; недоступное поле не штрафуется; искусственно испорченный транскрипт не даёт окончательного штрафа; отчёт калибровки перечисляет размер и происхождение выборки, версии моделей, матрицу расхождений и примеры ложных штрафов.

### 6.7. Подсказки и режимы обучения

- «Делай как я»: демонстрация действий и пошаговые подсказки; каждая подсказка и пауза — событие в истории; результат не смешивается с самостоятельным.
- Самостоятельный режим: подсказки о правильном действии не показываются до завершения; запрос помощи переводит попытку в «работу с поддержкой» и исключает её из самостоятельного рейтинга.
- После завершения — объяснение ошибок на основе замечаний: конкретная ошибка, доказательство, упражнение для исправления (Q&A 8, D-045).
- Подсказка не раскрывает эталон сверх того, что разрешено режимом.

**Приёмка:** один сценарий проходит оба режима; каждая подсказка видна в истории; результат с поддержкой не попадает в самостоятельный рейтинг.

### 6.8. Сложность

- Вектор факторов (шкала 0/1/2): неоднозначность исходных сведений, число существенных обстоятельств, число вовлечённых служб, объём необходимых дополнений, речевые осложнения разговора. Начальные веса равны; границы уровней утверждает преподаватель.
- ИИ предлагает вектор с объяснением по каждому фактору; публикует преподаватель. Сложность не меняет нормативы 30/180.

**Приёмка:** одинаковый вектор и версия весов дают одинаковую сложность; виден вклад каждого фактора; добавление осложнения не уменьшает сумму.

### 6.9. Профиль подготовки и рекомендации

- Профиль по пяти группам навыков D-032, отдельно по профилю ДДС, сложности и режиму. Входы — только проверенные попытки и экспертные поправки; технически нарушенные и непроверенные попытки профиль не снижают. Без истории — «недостаточно данных», старт назначает преподаватель.
- Рекомендация следующего задания — только из опубликованного и назначенного преподавателем пула; повышение не более чем на один соседний уровень на первых занятиях; при недостатке доказательств сложность сохраняется; при пустом пуле — понятная причина, **без генерации эталона на лету**.
- Выход модели проходит проверку схемы и ограничений; рекомендация не называется подтверждённой квалификацией.
- Аудит (C-08): каждая версия профиля и рекомендации хранит версии исходных оценок, версию правил агрегации и выбора, модель/шаблон, снимок пула, выбор, причину, режим автоприменения, действие преподавателя. Пересчёт не меняет уже начатую попытку. Прогон по сохранённым входам воспроизводит правило или сохранённый выход модели.
- Адаптация не даёт улучшить место в рейтинге выбором лёгкого задания (C-07).
- **Аналитика типичных ошибок группы ([ТЗ]):** для преподавателя — частота замечаний по типам D-037 и группам рубрики, по профилю ДДС и сложности; каждая цифра раскрывается до конкретных попыток. Считается только по `valid_score`; технические сбои показываются отдельно, не как ошибки группы. Отчёт ≤30 с.

**Приёмка:** каждый вывод уровня ссылается на попытки и версию модели; новый ученик не получает выдуманный уровень; рекомендации не выходят за пул и профиль ДДС; исправление оценки после автоматического выбора показывает исходное решение, обновляет следующий профиль и не меняет активный сценарий; `provisional` попытка не меняет профиль; групповая аналитика не считает технический сбой ошибкой.

### 6.10. База знаний и RAG

Статус: рекомендация команды для MVP, в ТЗ прямо не названа. Делай заменяемым модулем, без которого генераторы работают на явно переданных материалах.

- Источники: инструкция по карточке 112, скриншоты UI, классификатор ЕКП (1 281 правило / 90 полей, значения вместе с комментариями), РТУ Т16Р, учебно-методические материалы; условно — обезличенные выгрузки БД, статистика и журналы, если заказчик их даст. Исходники заказчика в репозиторий не коммитятся.
- Pipeline: загрузка → валидация → нормализация → обезличивание → контроль качества → версия корпуса → чанкинг → метаданные (источник, раздел, версия, дата, статус утверждения) → индекс (локальная embedding-модель через gateway).
- Поиск: запрос + фильтр версии → фрагменты со ссылками на источник. Генераторы (6.5) сохраняют, какие фрагменты использованы; версия корпуса входит в снимок версий сценария.
- 96 билетов до экспертной валидации и фиксации происхождения — кандидаты, а не нормативный эталон и не основание для auto-fail.
- Нормативная маршрутизация из RAG **не** берётся — только из движка правил.

**Приёмка:** офлайн-индексация и поиск; каждый фрагмент имеет источник и версию; смена версии корпуса не меняет опубликованные сценарии; в индексе нет персональных данных.

### 6.11. NLP-извлечение признаков

- Вход: текст описания, SMS, транскрипт речи. Выход: top-k типов происшествия с confidence, теги, слоты (адрес, число пострадавших, обстоятельства), пропуски обязательных сведений и противоречия.
- Низкая уверенность → предложение уточнить (для руководителя — переспросить), а не молчаливый выбор.
- Выход — подсказка для движка правил и оценивателя (`ML hints`); финальный тип, ЕКП и службы назначает только движок правил.
- Confidence — только если модель его отдаёт (инвариант 5).

**Приёмка:** противоречивое описание даёт флаг противоречия; отсутствующий адрес — флаг пропуска; изменение выхода NLP не меняет маршрут без изменения признаков, прошедших через движок правил.

## 7. Порядок работы (вехи)

Каждая веха заканчивается зелёными тестами, коротким отчётом в `docs/ai/progress.md` и коммитом.

- **M0. Каркас.** Структура `ai/` в репозитории, контракты (JSON Schema/pydantic) для событий попытки, реплик, `ack`, замечаний, критериев, профиля, рекомендаций; моки соседних модулей (маршрутизация, медиа, карточка); фреймворк инъекции отказов; CI-скрипт тестов. Выбор стека обоснуй в `docs/ai/adr/`; по умолчанию — Python 3.11+, локальный HTTP/WebSocket-сервис, llama.cpp-совместимый runtime для LLM.
- **M1. Руководитель без LLM.** Диалоговый автомат + детерминированный сценарный fallback в текстовом режиме; события C-05 в текстовом варианте. Цикл карточка → решение → разговор → подтверждение проходит без моделей.
- **M2. Голос.** STT и TTS через адаптеры, бенчмарк кандидатов на CPU, отчёт о лицензиях; голосовой цикл end-to-end через мок медиатракта; события `played_by_client`.
- **M3. LLM-реплики.** Формулировка реплик внутри разрешённых действий, валидатор выхода, защита от инструкций в реплике ученика, раздельные замеры задержек стадий.
- **M4. ИИ-оператор 112 и сценарии.** База знаний/RAG (6.10), NLP-извлечение (6.11), генерация карточек, черновиков сценариев и структурированных эталонов, gate публикации C-03, синтетический набор сценариев для выбранных ДДС, матрица покрытия.
- **M5. Оценивание и калибровка.** Семантические проверки D-034/D-036, грамматика, замечания D-037, `criterion_status`, стык с C-06, контрольная выборка и отчёт калибровки.
- **M6. Адаптация.** Подсказки, сложность, профиль, рекомендации, аналитика группы, аудит C-08.
- **M7. Доказательства.** Полная матрица отказов C-04, отчёт производительности, офлайн-прогон, таблица демо «живое / записанное / заранее подготовленное» (C-10).

Не переходи к следующей вехе, пока инварианты раздела 5 не покрыты тестами для уже сделанного.

## 9. Производительность и наблюдаемость

- Измеряй раздельно: транспорт аудио, завершение STT, генерация LLM, первый звук TTS, итоговая задержка до слышимого ответа. Фиксируй железо, модели, квантизацию, конкурентность, длительность, p50/p95/max, ошибки.
- Цели ТЗ сохраняются как контракт: UI ≤2 с до 100 пользователей, ≥20 одновременных сессий, передача голоса ≤150 мс. Не обещай 20 одновременно говорящих ИИ-диалогов на CPU без замера; ограниченный хакатонный прогон не удостоверяет полную нагрузку — перечисли непроверенное явно.
- Отчёт: `docs/ai/perf-report.md`. Метрики и статус компонентов доступны администратору; остановка inference видна.

## 10. Определение готовности

Работа считается выполненной, когда:

1. Все инварианты раздела 5 покрыты автоматическими тестами и тесты зелёные.
2. Матрица раздела 8 реализована; для каждого отказа C-04 задокументировано поведение.
3. Полный учебный цикл (уведомление → карточка → решение → голосовой звонок руководителю → подтверждение → оценка с объяснением → рекомендация) проходит локально без интернета на CPU-профиле.
4. Есть `docs/ai/perf-report.md`, `docs/ai/calibration-report.md`, `docs/ai/licenses.md`, ADR по выбору моделей, таблица демо C-10.
5. Каждая модель, промпт и шаблон версионированы, и версия сохраняется в попытке.
6. В отчётах явно перечислено, что **не** проверено и почему.

## 11. Чего не делать

- Не давать LLM выбирать службы, менять карточку, маршрут, балл или статус попытки.
- Не передавать эталон в промпт руководителя и в ответы обучаемому.
- Не использовать облачные API и не скачивать модели при запуске.
- Не объявлять конкретные модели STT/TTS/LLM утверждёнными до замера и проверки лицензий.
- Не выдумывать confidence, вероятность успеха, содержание отсутствующих билетов, факты сценария.
- Не превращать сбой модели или сети в ошибку ученика.
- Не заявлять эмулятор выполнением SIP-требования ТЗ, 150 мс — временем ответа модели, демо — доказательством SLA.
- Не перезаписывать транскрипты, оценки и основания; исправление — новая версия.
- Не встраивать логику соседних модулей в ИИ-контур; нет контракта — опиши черновик и замокай.
- Не коммитить исходники заказчика, реальные голосовые записи, веса моделей и секреты.
