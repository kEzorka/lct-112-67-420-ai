# Матрица покрытия синтетического набора сценариев (6.5, M4b)

Набор — `ai/data/synthetic/*.json` (9 файлов, узел E). Данные для этой матрицы проверяемы
программно: `ai/src/dds_ai/scenarios/coverage.py::coverage_cells()` строит те же ячейки из
живого набора сценариев, а `ai/tests/test_synthetic_coverage.py` сверяет, что документ не
разошёлся с кодом (при добавлении/удалении сценария тест упадёт, если эта таблица не обновлена).

Полный формат сценария и генератор — `docs/ai/agent-prompt.md`, раздел 6.5. Ни один сценарий
здесь не является настоящим билетом заказчика (D-050 — 96 билетов пока недоступны); все явно
помечены `provenance: "synthetic"`.

## 1. Решение диспетчера × профиль ДДС × состояние вызова

Три условных профиля ДДС (D-019 не отвечен заказчиком; профили — рабочее решение команды для
демонстрации покрытия, не приоритеты пилота): `dds-center`, `dds-north`, `dds-river`.

| Профиль ДДС | ответить (`respond`) | отказаться (`refuse`) | перенаправить (`redirect`) | диагностический (C-03) |
|---|---|---|---|---|
| `dds-center` | `syn-001` — соединение сразу | `syn-003` — обрыв после 2-й реплики | `syn-002` — «занято» → «не отвечает» → соединение | — (пробел) |
| `dds-north` | `syn-007` — соединение сразу, вариация описания | — (пробел) | `syn-005` — «не отвечает» → соединение | `syn-006` — маршрут не подтверждён (`unclassified_odor`, нет активного правила) |
| `dds-river` | `syn-004` — соединение сразу, допустимый пропуск факта | `syn-008` — обрыв после 2-й реплики | `syn-009` — «занято» → соединение | — (пробел) |

**Явные пробелы:**
- `dds-north` × «отказаться» с обычным (не диагностическим) сценарием — не покрыто.
- `dds-river` × диагностический — не покрыто; диагностический сценарий пока один на весь набор.
- `dds-center` × диагностический — не покрыто.
- Ни один профиль не покрывает «отказаться» + «не отвечает»/«занято» одновременно (отказ
  сочетается только с обрывом связи); отказ после проблем с дозвоном не проверен.
- Комбинация «занято» **и** «не отвечает» у одного сценария (как в `syn-002`) встречается
  только для `redirect`/`dds-center`; для других профилей проверяется не более одного состояния
  дозвона за сценарий.

## 2. Типичные ошибки диспетчера, которые проверяет сценарий

Сценарии сами не хранят «ошибку» — это то, что проверяет эталон/оцениватель по факту действий
обучаемого. Таблица показывает, какую ошибку позволяет обнаружить структура каждого сценария
(через `reference.expected_fields`, `reference.expected_decision`, `report_items`).

| Сценарий | Проверяемая типичная ошибка |
|---|---|
| `syn-001-fire-respond` | Пропуск обязательного элемента доклада (этажность — уточняющий факт руководителя); неверный тип происшествия |
| `syn-002-gas-redirect` | Неверное решение вместо «перенаправить»; необработанные состояния дозвона («занято»/«не отвечает») до соединения |
| `syn-003-repeat-refuse` | Ложный вызов службы при решении «отказать» (`routing.services` неприменим); работа с обрывом связи посередине доклада |
| `syn-004-flood-respond` | Пропущенный уточняющий факт (источник протечки) — руководитель должен ответить «неизвестно», если ученик не спросил; допустимый пропуск факта «этаж» в сгенерированной карточке (6.5) не должен трактоваться как ошибка карточки |
| `syn-005-transport-redirect` | Решение «ответить»/«отказать» вместо «перенаправить» при плановой заявке; необработанное «не отвечает» |
| `syn-006-unclassified-diagnostic` | Неспособность распознать неопределённость маршрута и всё равно назвать конкретную службу (диагностика C-03, не штрафуется по `routing.services`) |
| `syn-007-fire-respond-north` | Пропуск существенного обстоятельства (искры из электрощита) при перефразированном описании — проверка устойчивости к вариации (6.5) |
| `syn-008-flood-refuse-river` | Вызов службы при уже устранённой проблеме вместо решения «отказать»; обрыв связи не должен засчитываться как ошибка ученика (инвариант 4) |
| `syn-009-gas-redirect-river` | Решение «ответить» вместо «перенаправить» при бытовом запахе газа без пострадавших; необработанное «занято» |

**Явные пробелы:** структурное искажение адреса (частичное совпадение вместо точного) не
проверяется ни одним сценарием на уровне данных — это остаётся на семантический оцениватель
(M5, D-034) и не специфично для конкретного сценария. Сбой самой модели (STT/LLM/TTS) — не
свойство сценария, а инъекция отказа (C-04, `ai/tests/test_faults.py`, `test_supervisor.py`,
`test_cycle.py`), поэтому не отражён в этой матрице отдельной строкой.

## 3. Состояние на M4b

- 9 сценариев, 3 профиля, 3 решения диспетчера + 1 диагностический сценарий — соответствует
  диапазону 8–12 из задачи узла (`ai/tests/test_scenario.py::test_synthetic_set_is_marked_and_covers_all_decisions`).
- Диагностический сценарий (C-03) — ровно один (`syn-006`); недостаточно для проверки, что gate
  работает при разных профилях/решениях. Следующий шаг — расширить его число, если появится
  такая потребность у M5/M6.
- Расширение набора без обновления этой матрицы будет замечено тестом покрытия
  (`ai/tests/test_synthetic_coverage.py`), но тест не проверяет текст «Явные пробелы» — это
  остаётся ручной частью документа.
